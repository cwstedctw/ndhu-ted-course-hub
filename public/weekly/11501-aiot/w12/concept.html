雙腦合作：UNO Q 當大腦、ESP32 當手腳

ESP32＋EZ 擴充板＝感官和手腳（溫溼度、光線、旋鈕、A 鍵、燈、蜂鳴器……），UNO Q 的 Linux＝大腦（跑 Python：判斷、存檔、量延遲，以後可以接 AI）§〇 A·感官和手腳。兩塊板子用 WiFi 或 藍牙講話：WiFi 那條線走網頁問答的規矩（HTTP），板子回一段大括號的資料格式（JSON）；藍牙那條線走藍牙低功耗（BLE），大腦「寫入」一行字、板子主動通知（notify）回一行字。同一個大腦，換一條線就能用。

這頁最重要的是 §2 雙腦模擬器：左邊拉桿改環境，右邊看大腦每一輪印什麼、送了什麼。模擬器只畫先後順序、不放任何延遲數字——真的要多久，今天在真板上自己量。

每個事實後面標出處，對到本週內容規格（滑鼠停在標籤上看全名）： §〇 BESP32 那邊 §〇 CUNO Q 起始檔 §〇 D11/26 早上實跑 §〇 E怎麼連 ⚠️沒驗，照實標

      6.

    模擬器跟真的有哪裡不一樣
    
    
      
      
    • 一樣的：判斷規則（rules.decide()）、只送有變的（brain.py 的 apply()，跟「ESP32 上確定已經是這樣」比）、終端機那一行的欄位與寬度、記錄檔的欄位、網址與藍牙文字指令的字樣——都照 starter，check_concept.py 用同一批輸入讓網頁程式和 Python 對答案。
      • 
      
    • d10 的狀態大約每 2 秒才更新：WiFi 模式下大腦每秒問一次，常常連續兩輪拿到同一筆（模擬器每兩輪才換新值，終端機會看到同樣的數字）§〇 D·約每 2 秒更新；藍牙那條線的 temp 每次怎麼讀，模擬器照假板子每問一次就讀一次。
      • 
      
    • 沒有的：任何延遲數字；真的 DHT11 只給整數、光線旋鈕會抖（假板子有加一點抖動，這裡沒有，讓你看得清楚）。
      • 
      
    • 一輪多久：brain.py 預設 --period 1＝每秒一輪；模擬器的動畫速度跟這個無關。手機同時開 d10 的網頁會跟大腦搶連線（d10 一次只服務一個），想同時開就 --period 2 §〇 D·搶連線。
      • 
      
    • A 鍵連按兩下，在同一輪裡只算一次（大腦每輪只看「上一輪之後有沒有人按過」）§〇 D·連按兩下。

    4WiFi 和藍牙對照表
    
  
    上半是今天這兩課程式的實際行為（§〇 B），下半是課程規劃文件那張表的口徑規劃表。這裡不寫誰快多少、誰傳多遠：場地、距離、同時有幾組都會改變結果，數字今天自己量。最後一列填你量到的：一問一答來回的時間（RTT）的中位數。
    
  
    
    
    WiFi（第 10 課 d10_wifi_web.py）藍牙（第 11 課 d11_ble_remote.py）
    
    
    怎麼連上板子自己開基地台：WiFi 名稱 maker-XXXX、密碼 makerXXXX、網址 http://192.168.4.1；UNO Q 用 nmcli 連上去 §〇 B·第 10 課 §〇 E·去連 ESP32 的基地台藍牙名稱 maker-XXXX（OLED 第二行）；UNO Q 用 bleak 掃描名字、連上 §〇 B·第 11 課
    
    
    大腦讀得到GET /api/status 回 JSON：溫度、濕度、光線、旋鈕、三顆燈的狀態寫入 temp → 通知 temp 25 C, hum 61 %：溫度、濕度 §〇 B·寫入 temp
    
    
    大腦讀不到A 鍵（JSON 裡沒有按鈕）光線、旋鈕（所以門檻固定 28） §〇 B·讀不到
    
    
    板子會不會主動說不會，只會回答會：A 鍵按下／放開 → 按鈕特徵值通知 1／0 §〇 B·板子主動說
    
    
    叫它做事GET /api/led?name=red&on=1、/api/rgb?r=&g=&b=、/api/beep、/api/off寫入 red on／rgb 255 0 0／beep／off → 通知 OK red on、OK rgb、OK beep、OK all off；每個指令等自己的回話 §〇 D·等自己的回話
    
    
    雷第三顆燈在程式裡叫 blue，板子上是綠燈；溫溼度每 2 秒才讀一次；一次只處理一個連線 §〇 B·雷文字指令最多 128 位元組、回話截 100 位元組 §〇 B·雷
    
    
    適合什麼資料網頁、較密集資料、圖片、聲音、檔案 規劃表短命令、狀態、少量感測值 規劃表
    
    
    連線入口基地台／路由器、WiFi 名稱、網路上的門牌（IP）、埠號掃描、廣播、藍牙裡「服務＋特徵值」那套擺資料的方式（GATT）
    
    
    耗電通常較高通常較低 規劃表
    
    
    要不要網路通常要在同一個基地台；也可以由裝置自己開基地台（今天就是這樣）兩個裝置之間直接連
    
    
    教室裡的風險門牌號碼會變、校網隔離、帳密、基地台容量、斷線重連多塊板子名字混在一起、配對、藍牙被別的程式佔住 規劃表
    
    
    你量到的中位數

    5斷線長什麼樣子
    
  
    兩條線斷掉的樣子不一樣，但 brain.py 處理的方法一樣：這一輪算失敗、計數加一、下一輪再試；而且因為「不確定 ESP32 現在是什麼樣子了」，下一輪成功時燈號全部重送一次 §〇 D·燈號全部重送一次。在 §2 按「拔掉 ESP32 的電」就看得到。
    
  
    
    
    
      
    WiFi：問了沒人回
    
      
    每一輪都是一次新的問答，問不到就印：
    
      
    HH:MM:SS ESP32 沒回應（第 1 次）：timed out
    
      
    冒號後面那半句是 Python 給的錯誤說明，會隨情況不同。11/26 早上把電腦上的假板子關掉 3 秒再開，印的是 ESP32 沒回應（第 1 次）：<urlopen error [WinError 10061] …>，下一輪 送：red關、green開、彩色燈(255, 160, 60) 全部重送 §〇 D·假板子中途關掉 3 秒再開；真的 ESP32 拔電時後半句長怎樣，以你的畫面為準 ⚠️ §三·5。
    
      
    一直沒回應：先查 UNO Q 是不是還連在 ESP32 的 WiFi（nmcli -t dev status）、ESP32 是不是重開了。ESP32 重開後 UNO Q 會不會自己連回基地台，沒驗 ⚠️。
    
    
    
    
    
      
    藍牙：連線本身斷了
    
      
    藍牙是一條「連著」的線。斷掉時 link_ble.py 會叫醒正在等回話的人，這一輪印：
    
      
    HH:MM:SS ESP32 沒回應（第 1 次）：藍牙斷線了
    
      
    下一輪先印 藍牙斷線了，重新連線…，重新掃描名字。掃到就印 藍牙連上 maker-XXXX（…），但這一輪還是算失敗（ESP32 可能重開過、燈都滅了），印 ESP32 沒回應（第 N 次）：藍牙剛重新連上，下一輪重送燈號，下一輪燈號全部重送；掃不到這一輪也算失敗，冒號後面接 掃不到 maker-XXXX：ESP32 有在跑第 11 課嗎？名字（OLED 第二行）打對了嗎？ §〇 D·自動重新掃描重連。
    
      
    真的藍牙多久才發現斷線、斷線那一刻會不會先出現別的字樣，沒驗 ⚠️：今天拔電看看。藍牙「掃不到 maker-XXXX」先查：ESP32 是不是按住 A 開機、看到 OLED 顯示 BLE 才放開；手機程式是不是先連著它（一次只能一個中心）。
