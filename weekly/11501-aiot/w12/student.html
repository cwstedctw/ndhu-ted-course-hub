WiFi 線：網頁問答的規矩（HTTP）

大腦像用瀏覽器開網頁一樣，對 ESP32 送一個網址，ESP32 回一段字——這套「問一個網址、回一段答案」的規矩叫 HTTP。第 10 課開了這幾個網址：GET /api/status 回一段大括號的資料（JSON），欄位有 red、yellow、blue、rgb、temp、hum、light、knob、last、requests；/api/led?name=red&on=1 開紅燈（name 可以是 red／yellow／blue）、/api/rgb?r=&g=&b= 彩色燈、/api/beep 嗶、/api/off 全關。192.168.4.1 是 ESP32 在它自己那個網路裡的門牌（IP）。重點：ESP32 只會回答、不會主動開口——A 鍵被按了它也不會說，所以 WiFi 線讀不到按鈕。

藍牙線：寫入與通知

藍牙低功耗（BLE）連上之後，資料擺在「服務＋特徵值」一層一層的架子上（GATT）。第 11 課開了兩組：文字指令服務——大腦往 RX（6E400002-…）寫入一行字，ESP32 從 TX（6E400003-…）通知（notify）回一行字；按鈕（00001524-…）——A 鍵按下／放開，ESP32 主動通知 1／0。指令：temp → temp 25 C, hum 61 %（讀失敗回 DHT11 read failed）；red on → OK red on；rgb 255 0 0 → OK rgb；beep → OK beep；off → OK all off。一行指令最多 128 個位元組、回話截到 100 個位元組。UNO Q 的 Linux 用 Python 的 bleak 套件（起始檔 vendor/ 已經帶好；UNO Q 的系統 Python 沒有 pip，所以不用也不要自己裝），做的事跟手機 App 一樣。

為什麼「只送有變的」

大腦每秒想一次，但只有決定跟「ESP32 上確定已經是這樣」不一樣時才送：紅燈本來就亮著就不再叫一次，嗶聲只在「剛變熱」那一輪叫。哪一輪失敗了（逾時、斷線），大腦就不確定 ESP32 現在是什麼樣子，下一輪成功時把燈號全部重送一次。理由三個：① 每送一次就多一次一問一答，WiFi 線一次只處理一個連線、ESP32 忙著回你就沒空讀感測器；② 藍牙一行一行排隊，送越多越慢；③ 紀錄檔的 sent 欄乾淨，一眼看得出「哪一輪發生了事」。所以第一部分你看到滿滿的 沒變——那是好事。

為什麼這週 SSH 走 USB（192.168.7.2）

UNO Q 只有一張 WiFi 網卡。第二部分它去連 ESP32 的基地台，就離開了原本的網路；你要是用原本那個 WiFi 位址 SSH 進來，連線當場就斷。USB 線上那張網卡（W6 做的）跟 WiFi 無關，192.168.7.2 永遠在，所以今天一律走它。也因為這樣，起始檔要在連 ESP32 之前抓好——連上之後板子就沒有外網（日期也沒法校時，所以畫面時間是 5 月）。回原本的網路：用第 0 節記下的名字 nmcli connection up（不用 sudo）；原本就沒連 WiFi 就不用回。

UNO Q 怎麼把資料推給瀏覽器（第 5 節加碼）

一般網頁是瀏覽器問一次、主機答一次。webui.py 的網頁不一樣：瀏覽器一打開，就跟 UNO Q 開一條不掛斷的連線，UNO Q 每讀到一筆新資料、或 ESP32 的 A 鍵一被按下，就順著這條線送過去，瀏覽器不用一直問。所以 A 鍵按下去，遊戲角色馬上跳——那一下不用等大腦的下一輪。這條線斷了，網頁會寫「跟 UNO Q 斷線了，重新連線中…」，自己再接一次。整條路是：ESP32 →（WiFi 或藍牙）→ UNO Q 的 webui.py →（USB 線上的 192.168.7.2:8088）→ 教室機瀏覽器。

一問一答多久（RTT）、中位數、95%

「讀一次感測值來回」＝從大腦送出問題，到拿到答案的時間，叫來回時間（RTT）。每一輪量一次，停下來時排序：中位數是正中間那個（不怕偶爾一次特別慢），95% 在 … 內是「一百次裡九十五次都比這快」。假的 ESP32 的數字是電腦內部的，不代表 WiFi 或藍牙；真的數字今天你自己量（每塊板、每張桌子、每一次都不同）。紀錄檔是一行一筆的表格（CSV），read_ms 欄就是每一輪的來回時間、fail 欄 1＝那一輪讀取或送指令出錯、why 欄是理由；成功讀到的不到兩筆時不會印統計。另外：WiFi 線問到的感測值是 ESP32 大約每 2 秒更新一次的那一筆，所以每秒問會連續拿到同一筆；量到的是「一問一答多久」，不是「感測器多快」。
